# Macro allocation - assigning the SAS macro library to hvtiR* packages

Date: 2026-08-14
Status: approved, pending implementation plan
Evidence: `specs/artifacts/2026-08-14-macro-allocation.json`, generated by
`specs/artifacts/2026-08-14-macro-allocation-scan.py`

## Problem

The estate-wide map in
`hvtiRutilities:specs/2026-07-10-sas-macro-canonicalization-design.md` (on the
unmerged `spec/sas-macro-canonicalization` branch) decomposes the corpus "along
the `tp.<prefix>` naming convention". That is a **template** convention. Of the
180 files in `~/Documents/macro.library`, **3 carry a prefix**. So templates are
mapped and macros are not, and allocation has been happening one macro at a
time outside any rule: `hvtiRlifetables` was scaffolded from `%usmatchd` on
2026-08-13, `hvtiRtables` ported `%summarytable` on 2026-08-14.

This spec supplies the missing half.

## Scope

**Decides:** an owner for the `dc` prefix; the allocation rule; the shape and
regeneration of the map.

**Does not decide:** owners for the other unmapped prefixes; the fate of the
files those prefixes block; any code movement. Porting a macro to R remains
separate work - this says where a port belongs, not how to do it.

## Decision 1 - the file is the unit of allocation

Not the macro name. Three properties of the corpus force this:

- **64 of 180 files define more than one macro** (`xmacro.sas` defines 63,
  `desc_tab.sas` 28). Their internals are components, not independent units.
- **A template `%inc`s a whole file**, then calls one macro from it. All 17
  macros in `plot.sas` therefore have an include edge from every template that
  wants `%plot`. Any name-level rule classifies the 16 helpers as separately
  shared and scatters them.
- **290 macro names are defined in more than one file**, so the name is not a
  stable key. The file is.

## Decision 2 - named calls decide ownership; `%inc` only establishes reach

A template that writes `%usmatchd(...)` is stating intent about that macro. A
template that writes `%inc` of a file is invoking a mechanism - it pulls in
everything the file defines, including helpers it never uses.

So **ownership is seeded only by named calls**, and `%inc` edges are used only
to establish that a file is reachable at all. This distinction is load-bearing:
resolving ownership through include edges assigns `usmatchd.sas` to
`hvtiRutilities`, contradicting the `hvtiRlifetables` handoff that independently
identifies it as TemporalHazard work.

**Ownership does not propagate to dependencies.** A file needed by several
allocated files would otherwise inherit all their owners and look like a shared
utility - the same error by another route. Dependencies are classified
`travels-with-dependent` and move when the file that needs them is ported.

## Decision 3 - `dc` belongs to `hvtiRtables`

- `dc` is the largest single-owner block in the library.
- The family is coherent: `desc_tab.sas`, `desc_tab_02132012.sas`, `desc_tab_2012.sas`, `desc_tabma.sas`, `lr_trend.sas`, `std_coef.05012015.sas`, `std_coef.sas`, `std_coef_04252013.sas`, `std_dif.sas`, `std_dif_TEST.sas`, `std_dif_TESTma.sas`, `std_dif_wt.sas`, `std_dif_wt_vars.sas`, `std_difma.sas`, `summarytable.sas`, `summarytable_noempty.sas`, `summarytable_old.sas`.
- `hvtiRtables` already ported `%summarytable` and owns the
  `gtsummary`-consuming rendering half, so the receiving package is established
  rather than invented.

Other unmapped prefixes are deliberately left unowned - see Deferred.

## The rule

Applied to each of the 180 macro files:

| Tier | Condition | Destination |
|---|---|---|
| 1 | Named by templates of exactly one owned prefix | that prefix's package |
| 2 | Named by templates of two or more owned prefixes | `hvtiRutilities` |
| 3 | Named only by templates of unowned prefixes | blocked |
| 4 | Not named, but reachable from an allocated file | travels with that file |
| 5 | Not reachable at all | corpus-only |

Tier 2 is what "some of the macros belong in `hvtiRutilities`" means
operationally: shared is a computed property of the call graph, not a judgement.

## Validation

Three checks against independently-known answers, all of which distinguish this
rule from the variants rejected above:

| File | Rule says | Known truth |
|---|---|---|
| `summarytable.sas` | `hvtiRtables` | the macro `hvtiRtables` ported on 2026-08-14 |
| `usmatchd.sas` | `temporal_hazard` | matches the `hvtiRlifetables` handoff |
| `plot.sas` | `hvtiRutilities` | genuinely shared across many prefixes |

A name-level rule gets `plot.sas`'s helpers wrong; resolving ownership through
`%inc` gets `usmatchd.sas` wrong; propagating ownership to dependencies gets
`usmatchd.sas` wrong again. Only all three decisions together satisfy all three.

## Cross-package dependencies

The map records `needed_by` for every file, so a port can see what it will pull
from another package. There are 39 file-level cross-package dependencies, spanning 6 distinct
package pairs. The ones that matter most:

- `summarytable.sas` (`hvtiRtables`) needs `stddiff.sas` (`hvtiRdatasets`).
- `hazplot.sas` (`temporal_hazard`) needs `kaplan.int.sas` and `nelsonl.sas`
  (`hvtiRutilities`).
- `usmatchd.sas` (`temporal_hazard`) needs `dist.sas`, `phcurv9.sas` and
  `lgtphcurv9.sas` (`hvtiRdatasets`).

**One pair is circular** and must be resolved before either side is ported,
because R packages cannot have circular `Imports`:

- `hvtiRdatasets` <-> `temporal_hazard`

Resolution is a porting decision, not an allocation one: either the cycle is an
artifact of SAS files bundling several concerns, or the two belong in the same
package. Recorded here so it is discovered before the port, not during it.

## Corpus-only files (76)

They stay in `hvtiRtemplates` as reference and are allocated nowhere.

**This is absence of evidence, not evidence of absence.** The scan sees
templates, not the study programs copied from them, and a file used only by real
studies is indistinguishable here from one used by nobody. The single thing that
would overturn this classification is a scan of actual study directories; until
that is run, nothing should be deleted on the strength of this list.

## Deliverable

`specs/artifacts/2026-08-14-macro-allocation.json`, keyed by file, each entry
carrying its destination, tier, the prefixes that named it, its macros, and
which files need it. Regenerated by the committed scan, never hand-edited - when
a prefix gains an owner, the map is re-derived and the diff shows exactly which
files moved.

Hand-editing would let the map and the evidence disagree silently, which is the
defect class that produced eight documentation bugs in `hvtiRtables` the same
week this was written.

## Relationship to the canonicalization spec

This **amends** `2026-07-10-sas-macro-canonicalization-design.md` rather than
replacing it. That spec stays authoritative for templates and for the
`tp.<prefix>` to package map; this covers macros, the half it never addressed,
and adds one prefix owner (`dc`) to its table.

## Open decisions for the maintainer

2. Whether to scan study directories, converting the 76 corpus-only files from

   raises PHI-adjacent path questions, so it is out of scope here.
3. Whether `hvtiRtemplates` should re-vendor the corpus. Its README describes
