rfr-explain: Random forest regression: explain

Run sheet

What it does

Explains a saved regression forest: variable importance and dependence plots. See the report it produces on the gallery's synthetic study.

Prerequisites

  • A study. The job runs inside a study folder set up with _study.yml. Start a new study shows how.
  • The job it reads from. Render rfr-fit first, in this same set: the same subject and type as this job, which is how it finds what that job saved (rfr.rds). For a final render, render it final too: a final render refuses a hand-off saved from unregistered data.
  • Packages: randomForestSRC (>= 3.7.0), ggRandomForests (>= 4.0.0), hvtiRutilities. The job checks each floor when it starts, so an older library stops it at the top rather than partway through.
  • The hvti command. A long job starts from a terminal with hvti run; install_hvti() puts the command on your PATH, once.

Outline

These are the job's own sections, in order. The detail lives in the template: the comments at each EDIT: marker say what to set and why, and Work a job shows three ways to find them.

  1. Above the first section: 1 choice marked EDIT:.
  2. Study choices: 8 choices marked EDIT:.
  3. The forest: reads what rfr-fit saved (rfr.rds).
  4. Importance: fits and caches its results, so a later render reloads them (REFIT <- TRUE recomputes them).
  5. Dependence: a long fit that will not start in an interactive session, so the job runs in the background; fits and caches its results, so a later render reloads them (REFIT <- TRUE recomputes them).

Run it

Run it in the background. The fit is long, and a fit run in the console dies with the session. From a terminal in the study, hvti run 30_analyses/rfr.explain.<subject>.<type>.qmd (analyses/ in an older study whose folders carry no number) checks the job, then renders it in the background on the R the study's renv.lock records; add --final for the final render. From R, run_job(job) does the same. hvti status follows it and hvti cancel stops it. Once the fit is cached, its chunks run interactively and load it.

Render a draft as you go. render_job(job) runs the whole job in a clean R session and writes the report beside it. Render early and often: while any EDIT: marker is left, the report opens with a DRAFT banner listing them, and its numbers are not a result. Work a job explains why to render rather than run chunks by hand.

Then the final. Once no marker is left, render_job(job, final = TRUE) renders the accepted result. It refuses an open marker, a skipped chunk, stop_here() and unregistered data, and it records the job's provenance beside the report.
